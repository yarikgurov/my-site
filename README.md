# my-site — сайт-визитка с CI/CD

Сайт: https://yarikgurov.github.io/my-site/

Выполнили: Гуров Ярослав, Левин Артем, группа К841.

Простой сайт-визитка (HTML, CSS, JavaScript) с автоматической проверкой и развёртыванием на GitHub Pages через GitHub Actions. Пайплайн описан в файле `.github/workflows/ci-cd.yml`.

## Ответы на вопросы

### 1. Чем отличается CI от CD?

**CI (Continuous Integration, непрерывная интеграция)** — при каждом push или Pull Request код автоматически проверяется: устанавливаются зависимости, запускаются линтер, тесты и сборка. CI отвечает на вопрос «рабочий ли код».

**CD** — следующий этап, доставка готового кода пользователям. Continuous Delivery означает, что собранная версия всегда готова к выпуску, но развёртывание запускается вручную. Continuous Deployment означает, что после успешных проверок код публикуется автоматически. В этом проекте используется Continuous Deployment: после push в main сайт сам обновляется на GitHub Pages.

### 2. Что произойдёт, если тесты завершатся ошибкой на этапе CI?

Шаг `npm test` вернёт ненулевой код, задача `ci` завершится с ошибкой, и следующие шаги (сборка, загрузка артефакта) не выполнятся. Задача `deploy` не запустится, поэтому на сайте останется предыдущая рабочая версия. Во вкладке Actions запуск будет отмечен красным крестиком, а в логе будет видно, на каком шаге произошла ошибка.

### 3. Для чего используется директива `needs: ci` в задаче развёртывания?

По умолчанию задачи (jobs) в GitHub Actions выполняются параллельно. Директива `needs: ci` делает задачу `deploy` зависимой от `ci`: развёртывание начнётся только после того, как `ci` завершится **успешно**. Если проверка не прошла, развёртывание будет пропущено. Так непроверенный код не попадёт на сайт.

### 4. Что такое артефакт и для чего он передаётся между задачами?

Артефакт — это файлы, которые сохраняются после выполнения задачи. В нашем случае это папка `dist/` с собранным сайтом. Каждая задача выполняется на отдельной чистой виртуальной машине (runner), поэтому файлы из `ci` не видны в `deploy`. Задача `ci` сохраняет `dist/` через `upload-artifact`, а `deploy` получает его через `download-artifact` и публикует. Так на сайт попадает именно та сборка, которая прошла проверки, и её не нужно собирать второй раз.

### 5. Почему развёртывание не запускается на Pull Request?

У задачи `deploy` есть условие `if: github.ref == 'refs/heads/main'`. При Pull Request ссылка имеет вид `refs/pull/N/merge`, условие не выполняется, и развёртывание пропускается. Pull Request — это предложение изменений, которые ещё не приняты. Их нужно проверить (CI), но публиковать на сайт рано. Сайт обновится только после слияния изменений в ветку main.
